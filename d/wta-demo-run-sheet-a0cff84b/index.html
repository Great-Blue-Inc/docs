The one intro

Say once, then drive
Say

"So what we're demoing today is the opportunity email matching app we've put together. When a sender has just one open opportunity, it just matches on the email address, which is the same as any other provider. Where this is different is the multi-event scenarios. Match My Email handles those by requiring a name tag in the subject line. Ours reads the content of the email instead, things like the event date and names from the opportunity itself, and makes a suggestion based on logic we control, so you can give us feedback and we refine it over time. Anything it isn't sure about goes to a review queue where you see the ranked candidates and the reasoning on each. So today we'll walk the easy single-event case, then a multi-event case, inbound and outbound matching, and then text messages. Texts aren't fully set up yet, but we do have the webhook built, so you'd connect a service called Twilio that forwards texts to that endpoint, Salesforce receives them, and the same matching rules apply, and outbound texting can be set up through the same service. And the junk emails you mentioned, the ones that just say OK or thanks, those get filtered automatically but still show in a Filtered section so nothing is hidden, and that filter is keyword matching you control yourself in settings, right inside the app."

02

Multiple bookings, the actual logic

The differentiator, live

Two cases from the same problem: a sender whose address alone cannot decide.

Say

"So how the matching actually works is in two steps. It starts with identity, the email address, or the phone number for a text, and that finds the contact and their open bookings. If there's just one open booking, it's done, that's what you just saw. When the same person has several open bookings, identity isn't enough, so it reads the message itself and looks at things like the event date, words from the booking's name, and the type of event. If the evidence is strong it files itself, and if it's genuinely unclear it goes to the review queue for a person. Let me show you both."

Cue
Tell Claude: "run the strong match". Then refresh Match Review. An email from a planner (riley.hayes) lands already matched to the gala booking.
Say

"This sender is a planner with two open bookings, so the address alone can't pick one. But the message names the foundation gala and its date, so it filed itself against the gala booking. And if we expand Why this booking, you can see the event date in the message lines up with that booking and the words match the booking's name."

Cue
Tell Claude: "run the review case". Then refresh. An email from morgan.ellis lands in Needs review with ranked candidates.
Say

"Now here's the case where it's genuinely unclear. Same kind of sender, two open bookings, but this message just says checking on details for the holiday party. There's evidence, the words holiday and party match one booking's name, but it's not conclusive, so nothing gets guessed. It goes to the review queue with each candidate ranked and the reasons on each one. A person picks with one click."

Do
Click Confirm this Opp on the top candidate. Point at Undo this match on the result.
Say

"Confirmed, and if someone ever picks wrong, undo is right there. Nothing wrong ever saves itself silently. And this multi-booking case is exactly where the off the shelf tools fall down. Match My Email only matches on the address, and to pick between bookings their own docs require a special tag word in the email subject. Clients never type tag words. Einstein Activity Capture picks one by tiebreakers like close date without reading the message, and it never explains itself. This reads the message and shows its reasons."

04

Texts

Phase two, engine proven today

Frame it first, then fire the real delivery.

Say

"You said the number one priority is getting emails and texts captured into Salesforce. Text matching is part of this same build. There’s a webhook set up to accept text messages and run the same matching based on the contact’s number in Salesforce. It’s not connected to a phone number yet. You’d set up an account with a platform called Twilio, which routes text traffic to that webhook, and that’s what integrates it with Salesforce. I have a script here that simulates that inbound delivery."

Cue
Tell Claude: "fire the text". Then refresh Match Review. The text lands matched to Jamie's booking.
Say

"And in here we can see a match was made based on the phone number on the contact. It checks both phone fields and it tolerates formatting differences like dashes, spaces, or a country code. After that first step it’s the exact same rules you just saw on email, the event dates, the words from the booking name, the review queue when it’s unclear, the same junk filter, so it’s one engine across both channels. None of the off the shelf tools do texts at all. This piece just isn’t connected to a live number yet."

If asked, does texting work today

"Receiving and matching are built and tested end to end. What's left is connecting a phone number through Twilio." If asked about security: "the webhook only accepts requests carrying the phone company's cryptographic signature, so nothing fake can get in."

If asked, where do the messages live and is there room

"Every message is a real record in your Salesforce. This app is just a window over those records. Each match is stored as its own record with the message content, and the activity is logged on the opportunity. We verified against your production org before claiming this: you're using about 2.3 of your 10.7 gigabytes of data storage, and you logged about 3,600 emails in the last thirty days. At roughly two kilobytes a record that's under 100 megabytes a year. The headroom you have today covers decades." To show it live: Setup, then Storage Usage, in their org — or cue Claude: "pull the storage numbers" for the live counts.
