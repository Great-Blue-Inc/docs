Content Download flow, four fixes before activation

The Content Download flow turns content download form submissions into inbound sales opportunities, the highest volume inbound type in the org at roughly 10,800 existing opportunities. Four fixes were applied on Sep 15: the duplicate check now matches the opportunities the flow actually creates, the new opportunity carries the contact's account, it enters the Sales Development process at Open instead of landing mid-stage in the advertising pipeline, and the requester is linked with a contact role. If creation ever fails, Milad and Sean get an email instead of the form save breaking. The flow remains an inactive draft.

Requirements

Decisions from the flow review. The last three mirror the fixes already applied to the Demo, Trial, and Advertising request flows.

RequirementSolution
The duplicate check must match the opportunities the flow creates The lookup filtered on Lead Type Content Request, a value used by exactly 2 opportunities org-wide, while the create writes Content Download, the value on ~10,800. The check could never find the flow's own output, so every qualifying save would have created another opportunity. The filter now reads Lead_Type__c = "Content Download".
New opportunities must belong to the contact's account, and a failed create must never break the form submission The Create element now sets AccountId from the triggering contact, which the active Oppty_Non_Subsidiary_Account validation rule requires for every non-administrator user. Fault paths on both Create elements route to a Send Email action addressed to Milad Bonyab and Sean Martin with the contact, account, and exact error.
Content download opportunities must stay in the Sales Development pipeline at its first stage Record type changed from Advertising to Sales Development and stage from 3 - Qualifying to Open, matching where today's integration-created content download opportunities live. As built, new content leads would have landed mid-stage in the ad-sales pipeline, invisible to inbound triage.
The requesting contact must be linked with a real contact role A new Create Records element adds a primary OpportunityContactRole using the captured Id of the opportunity just created.

What changed

The canvas after the change

After (deployed Sep 15). The create continues into a new Create Opp Contact Role element, and both create elements carry red dashed fault paths into Email Milad & Sean on Failure. A failed create ends the flow quietly after the email, so the form submission itself still saves. The prior version was one straight line with no fault handling and no contact role.

The duplicate check, fixed

Lead Type = Content Download (was Content Request)

After (deployed Sep 15). The row outlined in red is the corrected filter on the Check for Current Content Download Opp lookup: Lead Type Equals Content Download, the value the create writes. The prior version filtered on Content Request, so the dedupe never matched anything the flow made.

Account ID ← Triggering Contact > Account ID

After (deployed Sep 15). The row outlined in red is the new first field assignment: Account ID = Triggering Contact > Account ID. The stage and record type changes sit below the panel fold, so the XML hunk below carries them.

Why there are no before screenshots

The Metadata API replaced the Sep 10 draft in place rather than stacking a new version, so the before version no longer exists in the org to screenshot. Its state is preserved as archived XML retrieved immediately before deployment, and the field-level delta below is taken from that archive.
