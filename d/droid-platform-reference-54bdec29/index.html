Bottom line for the engagement

Orientation

The five things that actually change how we plan and message this.

  • Droid is not a model, it is an agent harness (Factory's Claude-Code / Cursor competitor) that runs Claude, GPT, or Gemini per task. So building with Droid is not a downgrade from Claude. It can run on Claude.
  • Mark wants both roles. Droid as the runtime the partners and team use, and Droid as the tool we build with. Keep the two separate when we talk. Describing what we deliver, Droid is the runtime. Describing how we build, Droid is our tool.
  • Our layer = one MCP server over Salesforce. No native Salesforce connector exists, so we stand it up. Salesforce's own REST is the plumbing underneath. We are not building two APIs.
  • Cost resolves if Factory holds the seats. Vouchers grant a Factory plan with all models included, so usage runs on their subscription, not our API bill. Vouchers now redeem with no payment method required.
  • Partner registration maps cleanly to Missions, Skills, and Custom Droids. The architecture is known now. The specific actions come out of discovery.
What we told Factory

Salesforce as the source of truth, an MCP connection and actions Droid invokes to run the program, shape of the actions defined in discovery, run by them before anything is built. This doc is the technical backing for that message.

02

What Droid is, and the CLI

Verified · docs

Yes, there is a CLI like Claude Code. Interactive and headless.

The idea high level

Droid is Factory's agent-native coding tool. It spans an IDE plugin (VS Code, JetBrains, Vim), a terminal CLI, browser, Slack, and Jira. It routes across Claude, GPT, and Gemini per task. The design point Factory makes: agent design, not just the model, drives quality.

The CLI, end to end low level

  • Install: Homebrew (macOS / Linux), npm (Windows, and Linux needs xdg-utils).
  • Interactive: cd <project> && droid opens a full-screen TUI showing mode, autonomy, and MCP status.
  • Auth: browser sign-in on first run, or headless via export FACTORY_API_KEY=fk-... (generated at app.factory.ai/settings/api-keys), persisted in the shell profile.
  • Headless / CI: the droid exec path, for scripting and pipelines.
# headless usage
droid exec "prompt"                    # direct
droid exec -f prompt.md                # from a file
echo "task" | droid exec               # piped
droid exec --cwd <dir> --auto low "..." --output-format json

Autonomy tiers

none (read only) → --auto low (edits) → --auto medium (installs, builds, tests, commits) → --auto high (deploys, db writes) → --skip-permissions-unsafe (sandboxes only). Output formats: text, json, stream-json, stream-jsonrpc. Exit codes 0 / 1 / 2 like a normal CLI.

Config locations

  • AGENTS.md in a repo, for conventions the agent should follow.
  • ~/.factory/settings.json global config (BYOK models and more).
  • .factory/ dirs at project, folder, and user levels hold skills, droids, and mcp.json.

In our terminal, with the Salesforce CLI low level

Droid runs in the terminal on a project the same way Claude Code does now. It is not a Salesforce plugin. It executes shell commands, so it invokes the Salesforce CLI (sf / sfdx) like any other tool: pull and deploy metadata, run Apex tests, run SOQL, commit. Verified that Droid executes shell commands gated by the autonomy tier, so running sf is just a shell command. This is the same workflow shape we use today, and Droid can run Claude under the hood.

Guardrail

Point it at a sandbox. Keep deploys behind approval or --auto high, never full auto on an org that matters.

Coming from Claude Code high level

Most of our Claude Code mental model transfers directly. The concepts are the same, the names and paths differ, and Droid adds two things Claude Code does not have natively: multi-model routing and Missions.

Cost, billing, and vouchers

Two ways to pay high level

Factory sells subscription seats with pooled tokens, and separately supports BYOK where you bring your own model key. A plan's Standard Usage gives access to all models and is consumed first. Vouchers grant a plan, so all models are available out of the gate with no key of your own.

04

MCP setup

Verified · docs

How Droid connects to external tools and data. This is the mechanism our Salesforce layer plugs into.

The idea high level

MCP, the Model Context Protocol, is the open standard for giving an agent tools and data. An MCP server exposes actions (find record, update record, run query) that Droid calls. Droid is the client. Any MCP-capable agent can use the same server, which keeps our layer agent-agnostic.

Configuring it low level

Config file is mcp.json at three scopes: user ~/.factory/mcp.json, folder .factory/mcp.json (shared by nested projects), and project .factory/mcp.json at the repo root, committed. droid mcp add always writes to user config. Transports: stdio, http (recommended), sse (legacy).

{
  "mcpServers": {
    "my-server": {
      "type": "http",
      "url": "https://...",
      "headers": { "Authorization": "Bearer ${MY_TOKEN}" },
      "disabled": false,
      "disabledTools": ["tool1"],
      "timeout": 30000,
      "connectTimeout": 10000
    }
  }
}
  • Secrets: ${NAME} expands from shell env, only in env, headers, and oauth fields, never in command, args, or url. Keeps secrets out of the committed file.
  • Remote OAuth works zero-config via Dynamic Client Registration. Set oauth:false for header or API-key auth.
  • /mcp in-session lists the exposed tool names. Enterprise mcpPolicy can allowlist servers org-wide.
05

Connecting Droid to Salesforce

Our design · confirmReal scope

There is no native Salesforce connector. This is the layer we build.

Where it stands high level

Inferred: a docs search turns up Salesforce only as a SAML identity provider, not as a data integration. Factory's curated Connectors catalog (GitHub, Linear, Notion, Slack, Sentry, Google Workspace) does not list Salesforce. So this goes through a custom MCP server we stand up. That is real build-and-maintain scope, not a doc-covered integration.

The end-to-end pattern low level

  • Stand up a Salesforce MCP server (stdio or http) exposing tools for record CRUD, SOQL, and the partner-program domain actions.
  • Register it in project .factory/mcp.json with type:"http" and headers.Authorization referencing an env-var token, or type:"stdio" run locally with env holding the Salesforce credentials.
  • Scope which droid or subagent can see it via that droid's frontmatter mcpServers field.
  • Use disabledTools to trim the tool surface Droid loads into context.
The honest framing

Salesforce is the source of truth. The MCP server is the thin layer Droid operates through. Salesforce's native REST is the plumbing underneath. One layer, not two. The specific tools and actions come from discovery.

Missions, Skills, Custom Droids

Verified · mechanicsOur mapping

How an agent-driven partner registration workflow is structured.

The building blocks high level

Missions

/missions, a 5-phase orchestration for multi-feature work: planning, feature decomposition, skill integration, orchestrated execution via Mission Control. Scoped for 1 to 500 features. MCP, skills, and custom droids carry in unchanged.

Skills

Reusable SKILL.md procedures at .factory/skills/<name>/SKILL.md, with YAML frontmatter (name, description, allowed-tools, user-invocable). Auto-matched or slash-invoked.

Custom Droids

Subagents defined as .md files in .factory/droids/, frontmatter name, model, tools, reasoningEffort, mcpServers. Run non-interactively in isolated context.

AGENTS.md

Repo conventions the agent reads. Where we would encode the partner-program rules and guardrails.

Mapped to partner registration low level

Inferred design: a Salesforce MCP server (from section 05) → a custom droid "sf-partner-ops" scoped to only that MCP server plus edit and execute tools → a Skill "register-partner" encoding the intake, validate, create or update record, create task procedure → a Mission orchestrating the whole partner-program rollout across features (intake, dedup, approval tasks, notifications).

Auth, security, deployment

Verified · docs

How Droid safely acts on an external system, and where it can run.

  • MCP remote auth: OAuth via Dynamic Client Registration (zero-config), or header API keys via ${VAR} env expansion. System keyring stores OAuth tokens.
  • BYOK keys stay local, never uploaded to Factory. apiKeyHelper supports short-lived org-managed creds.
  • Deployment tiers: cloud-managed, hybrid (in your infra, your LLM gateway, your telemetry), or fully airgapped (no outbound internet, on-prem model endpoints).
  • Sandbox guidance: run higher --auto levels only in devcontainers, isolated VMs, or ephemeral CI, never a dev host directly.
  • Enterprise: mcpPolicy allowlists, autonomy URL overrides, custom CAs and mTLS, HTTPS_PROXY, EU data residency. Platform certs: SOC 2, ISO 42001, GDPR / CCPA, HIPAA-eligible, no training on your code.
08

Gotchas going in

Watch-outs

The things worth knowing before we scope the build.

  • Token budget: once a Salesforce MCP server exposes many tools, disabledTools matters. Every tool Droid loads costs context.
  • Governor limits are ours to handle: Droid's timeout and connectTimeout are client-side waits only. Salesforce API and governor-limit handling lives in the MCP server, not Droid config.
  • Project mcp.json entries cannot be removed via droid mcp remove, only by editing the file. Plan for how the client manages that repo file.
  • No native Salesforce connector. Budget the MCP server as real, ongoing build-and-maintain scope.
  • Vouchers redeem cleanly now, no payment method required (fixed 2026-08-27). Confirm the token allotment on the codes if heavy use is expected.
