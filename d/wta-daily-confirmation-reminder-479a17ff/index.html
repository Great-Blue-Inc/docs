02

What changed

Before (production, days 5 to 10). One update per line item. Salesforce groups line items 200 at a time and runs the groups side by side. Two groups held the same event on September 11 and one timed out. The days 1 to 4 flow has the same shape and is also retired.

After (Daily Confirmation Reminder). Starts on the event. One update covers all of its line items. The fault path retries once, then logs. Batch size 20. Event window 40 days back to 400 days ahead, pending your OK.

03

Proof and deploy state

Four sandbox runs on test events only, calendar invites to a test inbox only.

  • Run 1, logic. 26 events, 50 line items, 6 groups. All rows updated in 8 seconds. 0 faults. 10 of 10 calendars rewritten.
  • Run 2, production settings. 86 events, 290 line items, 5 groups of 20. All rows updated in 34 seconds. 0 faults, 0 lock waits. 40 of 40 calendars rewritten.
  • Run 3, event window 400 both ways. 12 gap cases, line items dated 3 to 395 days off their event. Every in-window row updated. Every out-of-window row untouched. 0 faults. 2 of 2 calendars rewritten.
  • Run 4, your 40 back and 10 ahead range. 7 cases. A line item 5 days out on an event ending in 20 days got no reminder, which is why the proposal keeps 400 ahead. 0 faults.
  • Production. Untouched. Both old flows active. The new flow passed a validate-only deploy against production with 0 errors (0AfUN00000AWWTd0AP).
  • Deploy plan. After your yes on the window and the status list: one more sandbox run and a validate-only pass, then deploy the new flow and deactivate the two old flows at a time you pick. Rollback is to reactivate the old flows.
